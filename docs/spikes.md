## Deviations from the design files

1. **`deploy` has `environment` default `prod`** in the live schema (enum `staging|prod|preview`); [07](design/07-mcp-vs-cli.md) said "no default". H3 treats a missing `environment` on `deploy` as `prod`.
2. **H3 MCP scope.** `send_agent_message` and `close_agent_chat` take only `chatId` (no `environment`), so the environment decision belongs to `start_agent_chat`; they are removed from the guard. `initialize_project` (creates a cloud project and writes files) and `submit_feedback` (sends text to Trigger.dev) are added: always `ask`.
3. **No `get_tasks` tool.** `trigger_task`'s description mentions it; the real tool is `get_current_worker`. Skills never name `get_tasks`.
4. **Extra read-only tools** the live server has beyond the design: `get_span_details`, `get_task_schema`, `list_agents`, `list_prompts`, `get_prompt_versions`, `read_session_channel`, `list_dashboards`, `run_dashboard_query`. `run-investigator` carries only `get_span_details` and `get_task_schema` of them; the rest are not granted to it (corrected in the second check, item 22).
5. **`start_dev_server`/`stop_dev_server`/`switch_profile` are annotated `readOnlyHint: true`** although they start a process or change state; the plugin does not trust annotations for safety decisions.
6. **`deploy --skip-update-check` context removed from H3.** The docs only say "Skip checking for `@trigger.dev` package updates"; they do not advise against it, so the plugin does not claim they do.
7. **`quiet` keeps the marker.** H1 writes the marker in `full` and `quiet` (printing only in `full`), so the script-alias half of H3 stays armed in `quiet`.
8. **Hook matchers are anchored** (`^(Edit|Write|MultiEdit)$`, `^(Bash|PowerShell)$`) because a matcher with regex characters is an unanchored regex.
9. **PowerShell alias handlers** call `node trigger-ctx.mjs guard --alias` directly (no `sh` gate) and check the marker in Node, so they work without Git Bash.
10. **The plugin's MCP server shows up in non-Trigger repos** (its instructions line is in context when the plugin is enabled at user scope), as the standing-cost table in 05 predicted; project-scope install avoids it.
11. **MIG-03 stopped flagging `onStart`, and that was wrong (corrected in round 2).** The catalog row listed `onStart:` as renamed to `onStartAttempt`; the migration guide still shows `onStart: ({ payload, ctx })` as current, so 0.1.0 dropped it. The installed 4.7.4 types say `@deprecated Use onStartAttempt instead` and the docs page has the heading "`onStart` function (deprecated)" (`tasks/overview.mdx`). MIG-03 now flags `handleError`, `onStart`, `init` and `cleanup` task options, as a hook-tier rule; the tool and stream APIs moved to the audit rule MIG-12.
12. **Precision fixes from the public-repo scan** (250 → 190 audit hits, 0 hook-tier changes): RT-12 and TSK-04 skip task directories and tests and are now S+J; RT-04 applies only to the Next.js App Router (hooks are fine in Remix/React Router); SCH-03 only flags string crons with a fixed hour; TSK-07 only flags dynamic imports of task modules, not `import("@trigger.dev/sdk")`; TSK-28 ignores `for await (… of runs.list())` pagination; TSK-24 became S+J; MIG-09 treats a caret range in the same major as satisfied (it resolves to the newest release); MIG-11 reads `package.json` only; CFG-08 treats a tsconfig without `include` (or with `**/*.ts`) as covering the config.
13. **Rules tied to a host or a framework.** Rules carry optional `target` (`cloud` or `self-host`), `frontend` (`next-app`) and `skip_paths`; `scan` applies them from the fingerprint. DEP-13 (self-host CI without `TRIGGER_API_URL`) only runs on a self-hosted target; SCH-06, DEP-07 and DEP-11 only on Cloud.
14. **Cross-file checks are code, not matchers.** `scripts/lib/builtins.mjs` implements TSK-26 (duplicate task ids), TSK-27 (tasks outside `dirs`), QUE-03 (undeclared queues), CFG-01/03 (browser or ffmpeg without the extension) and CFG-08; MIG-08 (version skew, any 3.x pin) is in `scan`. CFG-05, DEP-12 and WH-05 became judgment rules (a dashboard setting or auto-detection makes a static check unreliable).
15. **`audit --fix` round trip** (live, headless): a seeded git repo with 10 findings went to 7 after the command applied the three auto-fixable ones in two commits (MIG-01 and MIG-07 together as one family, CFG-08 separately), left the other 7 as flag-only findings, and left a clean tree with `trigger-audit/` git-ignored. MIG-04 stays flag-only although the design called it auto.
16. **Verified against the installed packages (4.7.4):** `defineConfig` is exported by `@trigger.dev/sdk` and by neither `@trigger.dev/sdk/build` (the export does not exist) nor `@trigger.dev/build` (root keys: `binaryForRuntime`, `esbuildPlugin`), which is what MIG-07 and the building-with-ai finding rest on.
17. **Live runs against Trigger.dev Cloud** (project `plugin-trigger-dev-sandbox`, created for this test in an org the maintainer authorised). `/trigger-dev:init` on a fresh `create-next-app`: config + task + signup route written, `start_dev_server` ready, `get_current_worker` listed the task, `trigger_task` (dev) reached COMPLETED with progress metadata 100, twice. `/trigger-dev:ship prod`: preflight clean, `deploy --env prod` produced version 20261020.1, `list_deploys` showed it DEPLOYED, `get_current_worker` (prod) listed the task. A deliberately failing task (`Promise.all` around two `triggerAndWait`) then ran in dev, and the `diagnose` skill with the `run-investigator` agent named the cause from the run's own span (`TriggerInternalError: Parallel waits are not supported…`), pointed at the exact line, gave the `batch.triggerByTaskAndWait` fix and the troubleshooting doc link, and flagged that the run still showed `executing`.
18. **What the live runs corrected.** `pnpm dlx … init -y` can stop with `ERR_PNPM_IGNORED_BUILDS` (pnpm 10 build-script approval); `init -y` does not add the `trigger.dev` devDependency, so `pnpm exec trigger deploy` fails until it is added; MCP `start_dev_server` needs the project **directory** as `configPath` (a file path gives `spawn ENOTDIR`); the Agent tool may start `run-investigator` in the background, so the skill now says to wait for it.
19. **Evals found two real bugs in the plugin, not in the graders.** Skill-relative paths such as `scenarios/x.md` were guessed wrongly by the model (now `${CLAUDE_SKILL_DIR}/…`), and `build` did not load for plain Trigger.dev questions (the description now says "answer questions … even for a quick question"). Models also guessed machine cost ratios (4x, 16x) when no docs were reachable, so the verified ratios now live in `references/limits.md`.

"> 0 vs official in every family" is **not met**: four families tie at 0.00, because both arms already score 1.00 there (the baseline model knows the standard realtime, webhook, migration and REST-caller APIs), so the suite has no headroom to show a difference. Negatives are at 100%. Plugin fixes the evals forced, all kept: full doc URLs in every answer (bare paths were not cited), shown commands always carry `--env`, an environments line in the session fingerprint, one question budget for the whole reply, cards loaded by absolute path, the verified machine-price table. H4 (failure-signature hook) stays deferred: no run showed the agent flailing on a CLI error.
21. **Blind audit of the tied cases.** Codex, asked why four families tie at 1.00, pointed out that mention-based regex graders can score a wrong answer 1.00 (a deliberately wrong migration answer passed all four `migrate-v3` graders) and named one check: regrade the tied cases' full outputs blind. Done for the six tied cases (migrate-v3, progress-bar, webhook-stripe, python-caller, browser-trigger, stream-llm-text), three runs per arm, 54 outputs. The outputs were shuffled with arm-revealing words scrubbed ("plugin", skill and command names); three Sonnet-high reviewers each wrote 5-8 must-have facts per case from the task and the pinned 4.7.4 docs before reading any output, then scored every output and listed verified errors. Unblinded: plugin **0.93**, no plugin **0.91**, official skills **0.85** (verified wrong items: 3, 3 and 7). So the ties are real saturation, not hidden lift or hidden harm: on these prompts the baseline model already writes correct code, and the plugin is not worse. Limits: the reviewers are the same model family as the assistants, nine outputs per case and arm is small, and scrubbing cannot hide every stylistic tell.

   What the audit found that no automated grader did: in `python-caller` only the plugin arm put a stable `idempotencyKey` in the REST call (3 of 3; 0 of 3 for the other two arms), and the plugin arm never gave the Python caller a way to read the run's status or result (0 of 3 vs 3 of 6). The `polyglot-caller` card now says to return the run id at once and expose a status route over `GET /api/v3/runs/{id}` (checked live: the endpoint returned `COMPLETED` with the output), and links `management/runs/retrieve`; after the change 4 of 4 reruns of `python-caller` include both the status route and the idempotency key, and the case now has a grader for the status route (the idempotency grader already existed). Across arms the most common real defect was an `@/…` import with no `tsconfig.json` alias in the fixture, which no arm checks.

   The plan's "+0.4 over all cases" target is not reachable for this suite as scored: with a no-plugin average of 0.70 the maximum possible lift over 42 cases is +0.30.

22. **Second check of 0.1.0 (a direct read of the shipped content, then fixes).** Two `haiku-high` agents checked about 340 claims in the chat-agent skill and playbooks, the 13 cards and the references against the pinned SDK 4.7.4 docs and the committed MCP snapshot (about 307 held); I re-verified every finding that mattered myself before changing anything. Nothing found here was caught by the eval suite, which scores answers to prompts, not the plugin's own text.

   *Hook bugs (both silent: the plugin did nothing).* (A1) The marker file that gates H2 and the script-alias half of H3 was written only by SessionStart, so a session that began in a repo without Trigger.dev and then ran `/trigger-dev:init` got no tripwire on the first tasks it wrote. `marker-gate.sh` now runs one shell-only signal check (`hooks/signal.sh`, shared with `session-start.sh`, without the `git ls-files` fallback) when no marker exists and writes the marker itself; the PowerShell path (engine called directly) does the same through `detect`. (A2) `tr -c` is per character under a UTF-8 locale on macOS and Node's `markerKey()` is per byte, so a project under `~/Masaüstü/...` got two different keys and the gate never found the marker; the shell side now uses `LC_ALL=C tr`. `tests/marker.test.mjs` (16 checks): 6 fail on `6030ede` (the non-ASCII and fresh-project cases), 0 on the fix. Live headless sessions, same prompts, old and new plugin: old = no tripwire for an empty project and for the `Masaüstü` path; new = the recorded tripwire text in both; a Go repo stayed silent. Cost: the gate in a repo without Trigger.dev went from a median of 13.2 ms to 17.0 ms (interleaved, 60 runs each, same harness), so the README says "roughly 10 ms".

   *Guidance that contradicted the docs (15 items, all fixed).* Chat: `chat.createSession` does support Head Start since 4.5.0 (the `ai-chat/backend` capability table is stale and says no; the card now names the conflict); with `storage` the resume cursors arrive as `changeset.cursors` in `save`, so the `lastEventId` write in `onTurnComplete` is redundant (CHT-13 text says which mode it applies to); approvals auto-submit with `lastAssistantMessageIsCompleteWithApprovalResponses`, not the tool-calls helper; `triggerConfig` is only gone from the transport; `@ai-sdk/otel` is optional tracing. Cards and references: waits over 5 s are unbilled while waits under 60 s keep the slot (the long-workflow card implied otherwise); `tasks.batchTrigger(id, items)` (the migration page's tuple form does not match the SDK types); `window: "0m"` is the 60-minute minimum on Free; SCH-05 now says `ttl` expires queued ticks and does not stop overlap; the run-scoped idempotency default holds inside a task only; most extensions affect deployed builds only (`pythonExtension` also acts in dev); Prisma has three modes; four cards still had bare doc paths (my earlier "all Docs lines are full URLs" was incomplete; now 167 cited pages resolve, 0 failures).

   *Claims settled live.* `trigger promote --help` shows `(default: "prod")`. `POST /api/v1/query` with a CLI PAT returned 401 "Invalid API key"; with the dev secret key, 200. With an empty profile directory, MCP `whoami`, `list_profiles`, `list_orgs`, `dev_server_status` and `stop_dev_server` did not answer within 60 s while `search_docs` did, and the CLI `whoami` answered "You must login first" in 2 s: the earlier claim that four tools work while logged out was wrong, and `init` and `doctor` now check the login with the CLI first.

   *Permissions and claims.* `init` pre-approved every `npx trigger.dev@latest` subcommand (including an explicit `deploy --env prod`, which the guard does not ask about); it now pre-approves `whoami`, `login`, `projects` and `init` per runner. `doctor` pre-approved `claude plugin *` (now `list`), `ship` pre-approved `git branch *` (now `--show-current`). `run-investigator` says what its Bash is for instead of claiming it has no write tools, and the claim in deviation 4 is corrected. The README no longer calls the 14 hook rules "high-precision": the corpus exercised one of them.

   *Not changed, on purpose.* `.mcp.json` stays `npx trigger.dev@latest mcp` (identical to Trigger's own config; the weekly snapshot diff is the guard). The prod guard still sees only the CLI, `package.json` scripts and MCP, not Makefiles or shell scripts. Windows without Git Bash is still untested.

   *Eval re-run for 0.1.1 (after the fixes above).* The plugin arm, all 42 cases, three runs each (`--ablation none`, 740 s, $9.59, no API errors, not partial); the no-plugin and official arms were not re-run because none of the edits touch them, so the Δ columns reuse the first full run. 23. **Round 2: does the plugin steer the agent? (0.2.0).** The second check (item 22) read the plugin's text. This one looked at what the agent actually does with it, using 121 leftover eval traces, the eval JSON, the public-repo hits, the installed SDK 4.7.4 types and about fifteen headless sessions. Seven new "steering-hard" eval cases (`evals/st-*`) were written first and run on 0.1.1 so each fix has a red baseline.

   - The only wrong-code failure the old suite showed (`v4-hooks`: `handleError`) had no edit-time check, and the same words sat in the migration card as current. `scripts/ci/sdk-surface.mjs` found the one place the plugin taught a deprecated name (the card's `onStart`), after two false-positive classes were handled (homonyms: the `concurrencyLimit()` function and the `additionalPackages` extension are current while the options of the same name are deprecated; config-level `onSuccess`/`onFailure`).

   - `build` did not load for plain edit requests ("add a task in trigger/…": 0 of 4 sessions, `st-implicit-fix` skill-fired 0 of 6). Step 7 (typecheck, login, a dev run, or UNVERIFIED) took it to 2 of 3 on a first run and 3 of 3 in the full run.
