# Maintainer rules (read before changing anything)

This is a Claude Code plugin. Its value is decisions, pitfalls and checks that stay correct as Trigger.dev changes. These rules keep it that way.

1. **Link, don't copy.** No pasted doc prose. A recommendation names the doc it comes from. API detail is looked up (`trigger-ctx docs`), not stored.
2. **Every hook answers six questions** (event, trigger condition, what it injects or blocks, the failure it prevents, cost, why not a skill) in `docs/design/05-steering-and-hooks.md`. A hook that cannot answer them does not ship. Hooks stay silent outside Trigger.dev projects and set `onFailure: "continue"`.
3. **Hook text is facts, not orders.** Hook output arrives as a system reminder; write "streamText imported from ai bypasses the managed stream", not "you must…". Cap: H1 700 characters, H2 5 hits and 1,500 characters.
4. **Rules are data.** Add or change a rule in `scripts/rules/src/*` (hook tier: `hook-rules.mjs`), then `node scripts/rules/build.mjs && node scripts/rules/render-catalog.mjs`. Every rule that has a matcher needs `examples.bad` (must hit) and `examples.good` (must stay silent); `node tests/rules.test.mjs` enforces it. **Hook-tier rules need ≥ 95% precision** on real Trigger.dev repos and an `applies_when` gate where the API is version-dependent; a rule that fails the bar moves to the audit tier. The 60-repo corpus exercised MIG-01, MIG-02 and MIG-03 of the 15 hook rules; the other 12 rest on their fixtures until a corpus hits them, and the README says so. The engine locates; an agent judges.
5. **`hooks/hooks.json` is generated.** Edit `scripts/build-hooks.mjs` or the guard's tool tables, then `node scripts/build-hooks.mjs`. CI runs `--check`.
6. **MCP tools.** `scripts/ci/mcp-tools.snapshot.json` is the committed `tools/list` of the official server. When the weekly job reports a diff, update the guard tables (`scripts/lib/guard.mjs`), `agents/run-investigator.md` and `references/mcp-vs-cli.md`, then refresh the snapshot with `node scripts/ci/mcp-tools-snapshot.mjs > scripts/ci/mcp-tools.snapshot.json`.
7. **Skills.** Model-invocable skills (`build`, `chat-agent`, `diagnose`, `ship`) cost listing tokens in every session: keep descriptions scoped to Trigger.dev contexts and never add another one without a negative eval case (`ship` has `st-neg-app-deploy`: deploying the app itself must not start it). `ship` is model-invocable because a plain "deploy the jobs" never loaded `build`, and the preflight is the safe path; the prod guard still asks on an implicit environment. Everything else with side effects is `disable-model-invocation: true`. Skill shell injections (`!`) use `node "${CLAUDE_PLUGIN_ROOT}/scripts/trigger-ctx.mjs"`: the bare `trigger-ctx` is not on the PATH of that shell (measured in the eval harness). SKILL.md ≤ 1,200 words, critical rules first (after compaction only the first 5,000 tokens of an invoked skill are re-attached). YAML descriptions must not contain `: `; the validator does not check skill frontmatter, so `python3` + PyYAML does (CI).
8. **Cloud first, self-host safe.** Never hard-code `https://api.trigger.dev` in advice or code; read `TRIGGER_API_URL`. Cloud-only advice carries a flag. A feature the docs label beta, early access or preview is never the default recommendation and always has a stable fallback; register its doc path in `BETA_PAGE` (`scripts/lib/docs.mjs`) so `trigger-ctx docs` says so. No page is beta today: hosted webhooks, Slack/Linear agents, channels and `chat.event` left private beta in SDK 4.8.0 and are gated by `since: 4.8.0` in `references/link-index.md` instead.
9. **Versioning is automatic.** Installed copies update only when the version string changes, so `.github/workflows/release.yml` runs `scripts/release.py` after `ci` is green on `main` (the same two files every plugin repo of this owner vendors; canonical copy in `plugin-agentic-maker`). It reads the conventional-commit subjects since the last release tag: `feat` = minor, `fix`/`perf` = patch, `type!:` or `BREAKING CHANGE` = major (minor while < 1.0.0); `docs`, `ci`, `chore`, `test`, `style`, `build`, `refactor` = no release; a commit that touches only docs, tests, evals, `.github/` or root markdown never releases. Then it bumps every manifest together, writes the `CHANGELOG.md` section, validates the tree with `claude plugin validate --strict`, commits `chore(release): v<x.y.z> [skip ci]`, tags `v<x.y.z>` and `trigger-dev--v<x.y.z>` and publishes the GitHub release. Write conventional subjects. To choose the number or write the changelog yourself, bump the manifests and add the `## <version>` section in your commit: that exact version is released. To release something the rules skip (a README fix that should reach installed copies), run the `release` workflow by hand with a level.
10. **Before you push:** `node tests/rules.test.mjs && node tests/guard.test.mjs && node tests/detect.test.mjs && node tests/seed.test.mjs && node tests/replay.test.mjs && node tests/marker.test.mjs && node scripts/build-hooks.mjs --check && claude plugin validate --strict .`
11. **Facts versus assumptions.** `docs/spikes.md` records what was measured and where the build differs from `docs/design`. Add to it when a measurement changes a decision.
12. **Recordings.** `tests/recordings/*.json` hold what real headless sessions sent to the hooks and what the hooks answered (`--include-hook-events`). `tests/replay.test.mjs` replays them through the real entry points. When you change hook wording on purpose, run a live session, copy the new outputs into a new dated recording, and say so in the commit; never edit expected text to make the test pass.
13. **Names are checked against the SDK's own types.** `node scripts/ci/sdk-surface.mjs [<node_modules/@trigger.dev>|--latest]` lists names the installed types mark `@deprecated` and `tasks.foo`-style members they do not declare, and flags every line in `skills/` and `references/` that teaches one as current (weekly job against `@latest`). Run it before a release. A cited doc page can be stale where the types are not (`onStart` was shown as current in the migration guide while the 4.7 types deprecate it).
14. **Always the latest, never a pin.** The plugin tracks the newest Trigger.dev release: new projects and packages install at `@latest` (never a version copied from this plugin or from memory), templates use `latest`, and the plugin's text carries a version only as a `since` gate or as evidence ("measured on 4.8.1"). When the installed SDK is older than the newest, `build` and `doctor` say how far behind it is (`trigger-ctx detect --brief --latest`) and offer `npx trigger.dev@latest update`; they never run it unasked. A user may pin on purpose, for example at deploy time; the plugin notes it once and respects it. Eval fixtures are the one place a version is frozen on purpose, because a case must be reproducible.
15. **Keep up with upstream.** Read "Keeping up with upstream" below before changing any guidance. `references/upstream.json` records the release the plugin was last reconciled with; `scripts/ci/upstream-check.mjs` says what is newer and which of our files each change touches.

## Keeping up with upstream

Trigger.dev ships a release about every few days (SDK, CLI and MCP server share one version number), and the docs move with it. The plugin is correct only for the release it was last checked against, so the job is a loop: **notice → classify → change the one place that owns the fact → prove it → record the new baseline.** This is the model; follow it before editing anything.

### 1. What "upstream" is, and which source wins

| Surface | Where to read it | Trust it for |
|---|---|---|
| **The SDK's own types** (`node_modules/@trigger.dev/sdk/dist/**/*.d.ts`, `@deprecated` notes) | `npm pack @trigger.dev/sdk@latest` | What exists and what is deprecated. Wins over everything. |
| **Docs bundled in the package** (`node_modules/@trigger.dev/sdk/docs/**.mdx`) | the same tarball | Behaviour and API shape for that exact version. |
| **Docs site** (`https://trigger.dev/docs/llms.txt`, each page plus `.md`) | web | Pages the tarball does not carry; wording of limits and plans. |
| **GitHub releases** (`triggerdotdev/trigger.dev`, tags `v4.x.y`) | `gh release view v4.8.1` | What changed and when (the notice), not how it behaves. |
| **MCP server** (`npx -y trigger.dev@latest mcp`, `tools/list`) | `scripts/ci/mcp-tools-snapshot.mjs` | The tool names, parameters and defaults the guard must know. |
| **CLI** (`npx trigger.dev@latest <cmd> --help`) | the CLI | Flags and defaults, which the prod guard depends on. |
| **Connector packages** (`@trigger.dev/slack`, `@trigger.dev/linear`, `@trigger.dev/build`, `@trigger.dev/react-hooks`) | npm | Packages that share the version number but are not the SDK. |

Order of trust when they disagree: types, then bundled docs, then the docs site, then release notes, then memory. A page can be stale where the types are not (`onStart` was taught as current while the types deprecated it), and a release note is a headline, not a spec.

### 2. The loop

1. **Notice.** `node scripts/ci/upstream-check.mjs` compares `references/upstream.json` with npm and the GitHub releases and prints every new release-note line with the files it probably touches. The weekly `freshness` workflow and the local weekly job (below) run it; exit 1 means something is newer.
2. **Classify each line** with the table in section 3. Most lines are fixes that change nothing here. The ones that matter: a new or renamed API, a changed default, a deprecation, a feature leaving beta, a new MCP tool, a new CLI flag, a security release that needs a redeploy.
3. **Diff the evidence, not the headline.** Unpack the old and the new tarball and diff `docs/` and the `.d.ts` files (`diff -ru old/package/docs new/package/docs`). Compare MCP snapshots (`node scripts/ci/mcp-tools-snapshot.mjs | diff scripts/ci/mcp-tools.snapshot.json -`). Run `node scripts/ci/sdk-surface.mjs --latest` and `node scripts/trigger-ctx.mjs links-check --anchors`. The question to answer each time: *what did a user have to do or avoid before that they now do differently, and which of our files says the old thing?* Grep the plugin for the old wording (`grep -rniE "beta|<old name>" skills agents references`).
4. **Change the single owner of the fact** (section 3), then everything that quotes it. Do not paste doc prose; link and gate (`since:` in the link index, a `**Gates:**` line on the card).
5. **Prove it.** Run the tests (rule 10). Run the live check for what you changed: a guard change is run through `trigger-ctx guard` with a real hook payload, a card change is exercised by an eval case or a headless session that should now behave differently (`evals/`, see "Why tests"). Write down what you saw.
6. **Record the baseline.** Update `mcpToolCount` and run `node scripts/ci/upstream-check.mjs --write`, refresh the MCP snapshot, and commit with a conventional subject (`feat:` when behaviour or guidance changed, `fix:` for corrections, `docs:` for nothing shipped). The release workflow does the rest (rule 9).

### 3. Where each kind of change lands

| Upstream change | Owner of the fact | Also touch |
|---|---|---|
| A feature leaves beta or arrives | its scenario card in `skills/build/scenarios/` or playbook in `skills/chat-agent/playbooks/` (`**Gates:**` line says the SDK version) | `references/link-index.md` (`since`), `skills/build/discovery.md`, `BETA_PAGE` in `scripts/lib/docs.mjs`, `README.md`, the eval case for it |
| New or renamed API, option or deprecation | `references/traps.md` (deprecated names) and the card that teaches it | a rule in `scripts/rules/src/` (hook tier only with ≥ 95% precision and an `applies_when`), `scripts/ci/sdk-surface.mjs` run |
| New MCP tool or parameter | `scripts/ci/mcp-tools.snapshot.json` | guard tables in `scripts/lib/guard.mjs` (write, always-ask, environment-aware), `node scripts/build-hooks.mjs`, `agents/run-investigator.md` (read tools only), `references/mcp-vs-cli.md` |
| New CLI command or flag, or a changed default | `references/mcp-vs-cli.md` | `scripts/lib/guard.mjs` (`SUBCOMMANDS`, `hasExplicitEnv`), `tests/guard.test.mjs`, `skills/build/verify.md`, `skills/ship/SKILL.md` |
| Changed limit, plan or price | the card's `**Gates:**` line | `references/link-index.md` flags (`plan`, `cloud`) |
| New docs page | `references/link-index.md` row (key phrases, pages, `L` when the tarball bundles it, `since`) | the card that should cite it |
| Security release | `skills/ship/SKILL.md` (redeploy note), `skills/diagnose/symptoms.md` | nothing else |
| New package that shares the version number | `references/upstream.json` `packages`, the relevant playbook | `scripts/lib/detect.mjs` features list when it should show up in the session facts |
| Dashboard-only change (alerts UI, billing) | `skills/diagnose/SKILL.md` human gates | nothing else |

When a line fits no row, read the release note and the docs page it links; if a user's code or commands would change, add a row to this table in the same commit.

### 4. Cadence and automation

- `.github/workflows/freshness.yml` runs weekly (Monday) in CI: links and anchors, llms.txt coverage, bundled-docs parity, deprecated names in `skills/`, the MCP snapshot and `upstream-check`. A red run is the notice.
- `scripts/maintenance/weekly.sh` is the local counterpart. A macOS LaunchAgent (`scripts/maintenance/install-weekly.sh`) runs it weekly and at login when a week has passed, so a sleeping or rebooted machine catches up. It clones the repo fresh, runs the checks, and only when something drifted starts a headless Claude Code session in the clone with this section as its brief; the result goes through a pull request, CI, and a merge on green. It writes `~/Library/Logs/trigger-dev-weekly.log`. `touch ~/.claude/trigger-dev-weekly.off` stops it.
- Whoever (or whatever) runs the loop ends it by running `upstream-check` once more: exit 0 and a changed `references/upstream.json`.

## Why tests, and which ones are necessary

A plugin has three kinds of content, and each fails differently, so each is checked a different way. Do not add a test that does not belong to one of these.

1. **Deterministic code** (the guard, the detect engine, the lint rules, hook generation, the release script). It either returns the right answer or it does not, and a wrong answer is expensive: the guard decides whether a production deploy goes through, a noisy rule teaches users to ignore the hook. These get unit-style tests that run in seconds with no network and no model: `tests/guard.test.mjs` (every decision the guard can make, including the recorded live ones), `tests/rules.test.mjs` (each rule fires on its bad example and stays silent on its good one), `tests/seed.test.mjs` (the rules against seeded bad code, so a refactor cannot silently drop a rule), `tests/detect.test.mjs` (project fingerprints for each stack), `tests/marker.test.mjs` (hooks stay silent and fast outside Trigger.dev projects), `tests/replay.test.mjs` (what real sessions sent the hooks, replayed through the real entry points; this is the guard against changing hook wording by accident), `node scripts/build-hooks.mjs --check` (generated file matches its source). They are necessary because nothing else would notice a regression until a user did. **Add a case whenever you change guard or rule behaviour**, as part of the same change.
2. **Text that steers the model** (skills, cards, playbooks, agent prompts). A string cannot be unit-tested; what matters is what the model does with it. The check is an eval: a prompt, a fixture project, and graders (`evals/<case>/`), run headless against the plugin and against no plugin. Evals cost money and are noisy, so they are not in CI. Run the cases that touch what you changed (and the negatives, which must stay at 1.00); run the whole suite before a release that changes steering broadly. Cases are named for the behaviour (`webhook-stripe-hosted`: on SDK 4.8.1 the answer must be a hosted endpoint, `webhook-stripe`: on 4.7.4 it must be the fallback route plus an update offer).
3. **Facts about the outside world** (doc links, API names, MCP tools, versions). These do not fail because we changed something; they fail because Trigger.dev did. A test written once cannot catch that, so these are freshness checks that run on a schedule against the live sources (`freshness.yml`, `upstream-check`), report drift, and never block a change.

What we deliberately do not test: the wording of skills (reviewed by reading), a copy of the docs (we do not hold one), and anything that only restates a type the compiler already checks (`ci.yml` typechecks the init templates against the newest SDK instead). If a test needs updating more often than the thing it protects changes, delete it.
