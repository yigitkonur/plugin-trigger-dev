# Maintainer rules (read before changing anything)

This is a Claude Code plugin. Its value is decisions, pitfalls and checks that stay correct as Trigger.dev changes. These rules keep it that way.

1. **Link, don't copy.** No pasted doc prose. A recommendation names the doc it comes from. API detail is looked up (`trigger-ctx docs`), not stored.
2. **Every hook answers six questions** (event, trigger condition, what it injects or blocks, the failure it prevents, cost, why not a skill) in `docs/design/05-steering-and-hooks.md`. A hook that cannot answer them does not ship. Hooks stay silent outside Trigger.dev projects and set `onFailure: "continue"`.
3. **Hook text is facts, not orders.** Hook output arrives as a system reminder; write "streamText imported from ai bypasses the managed stream", not "you must…". Cap: H1 700 characters, H2 5 hits and 1,500 characters.
4. **Rules are data.** Add or change a rule in `scripts/rules/src/*` (hook tier: `hook-rules.mjs`), then `node scripts/rules/build.mjs && node scripts/rules/render-catalog.mjs`. Every rule that has a matcher needs `examples.bad` (must hit) and `examples.good` (must stay silent); `node tests/rules.test.mjs` enforces it. **Hook-tier rules need ≥ 95% precision** on real Trigger.dev repos and an `applies_when` gate where the API is version-dependent; a rule that fails the bar moves to the audit tier. The engine locates; an agent judges.
5. **`hooks/hooks.json` is generated.** Edit `scripts/build-hooks.mjs` or the guard's tool tables, then `node scripts/build-hooks.mjs`. CI runs `--check`.
6. **MCP tools.** `scripts/ci/mcp-tools.snapshot.json` is the committed `tools/list` of the official server. When the weekly job reports a diff, update the guard tables (`scripts/lib/guard.mjs`), `agents/run-investigator.md` and `references/mcp-vs-cli.md`, then refresh the snapshot with `node scripts/ci/mcp-tools-snapshot.mjs > scripts/ci/mcp-tools.snapshot.json`.
7. **Skills.** Model-invocable skills (`build`, `chat-agent`, `diagnose`) cost listing tokens in every session: keep descriptions scoped to Trigger.dev contexts and never add another one without a negative eval case. Everything with side effects is `disable-model-invocation: true`. SKILL.md ≤ 1,200 words, critical rules first (after compaction only the first 5,000 tokens of an invoked skill are re-attached). YAML descriptions must not contain `: `; the validator does not check skill frontmatter, so `python3` + PyYAML does (CI).
8. **Cloud first, self-host safe.** Never hard-code `https://api.trigger.dev` in advice or code; read `TRIGGER_API_URL`. Cloud-only advice carries a flag. Private-beta features (hosted webhooks, Slack/Linear, channels) are never the default recommendation and always have a fallback.
9. **Versioning.** Bump `version` in both `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` together, and add a `CHANGELOG.md` entry.
10. **Before you push:** `node tests/rules.test.mjs && node tests/guard.test.mjs && node tests/detect.test.mjs && node tests/seed.test.mjs && node tests/replay.test.mjs && node scripts/build-hooks.mjs --check && claude plugin validate --strict .`
11. **Facts versus assumptions.** `docs/spikes.md` records what was measured and where the build differs from `docs/design`. Add to it when a measurement changes a decision.
12. **Recordings.** `tests/recordings/*.json` hold what real headless sessions sent to the hooks and what the hooks answered (`--include-hook-events`). `tests/replay.test.mjs` replays them through the real entry points. When you change hook wording on purpose, run a live session, copy the new outputs into a new dated recording, and say so in the commit; never edit expected text to make the test pass.
